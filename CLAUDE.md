# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Unity project for a roguelike dungeon generator (ローグライク風ダンジョンジェネレーター). The core deliverable is an embedded UPM package at `Packages/DungeonGenerator` (`jp.xeon.rogue_like_dungeon_generator`); the `Assets/` folder contains only editor utilities and a sample scene. Unity editor version: 6000.0.36f1 (see `ProjectSettings/ProjectVersion.txt`). Comments, logs, and UI labels are written in Japanese — keep that convention.

## Development Workflow

There is no CLI build or test setup. Development happens inside the Unity Editor:

- Testing is done manually via editor windows under the **Debug/DungeonGenerator** menu (defined in `Packages/DungeonGenerator/Editor/`): フロア生成テスト (`FloorGenerateTester`), plus testers for A*, root finding, and terrain generation. These render the generated map with colored `EditorGUI.DrawRect` cells.
- The solution `RogueLikeDungeon.sln` is generated by Unity; don't build it directly to validate changes — Unity recompiles on focus.
- `Assets/Scripts/Editor/ScriptImportPostProcessor.cs` auto-converts imported `.cs` files to UTF-8 (Japanese encoding detection via `EncodeHelper`). Always save `.cs` files as UTF-8.

## Architecture

All runtime code lives in `Packages/DungeonGenerator/Runtime/Scripts/` under three namespaces:

- **`Xeon.Dungeon`** (Dungeon/ and Data/) — generation pipeline and data model
- **`Xeon.RootFinder`** (RootFinder/) — pathfinding: `AStar`, `Dijkstra`, and `BackTracking` (used to detect isolated rooms)
- **`Xeon.Utility`** (Utility/) — `TerrainGenerator` (weathered/natural terrain), `Encyclopedia<K,V>` (serializable Dictionary), extension methods

### Generation pipeline

Entry point is `DungeonGenerator.GenerateFloor(width, height, maxRoom, deletePathPercent, weatheringRate)`:

1. **BSP split** — `Area` recursively splits the map into areas (static `Area.Count` / `Area.MaxRoomNum` control recursion; they are reset at the start of each generation — beware this static state).
2. **Room creation** — each leaf `Area` creates one `Room` with margins.
3. **Adjacency + paths** — areas build adjacency lists, then `Path` objects connect rooms of adjacent areas (horizontal/vertical corridors).
4. **`FloorData`** assembles the tile map (`TileData[,]`): base terrain comes from `TerrainGenerator` when `weatheringRate > 0` (mix of Wall/Water/Hole), and original terrain is stored in `terrainData` so deleted corridors can be restored to their pre-corridor tiles.
5. **Path deletion** — `FloorData.DeletePath` randomly removes corridors, then uses `BackTracking.FindIsolatedRoom` to restore paths until no room is unreachable (retry cap of 100).

`ApplyMap` layering order matters: deleted paths (restore terrain) → paths → rooms.

### Data model notes

- `TileData<T>` / `DungeonSetting<T>` / `TileSetting<T>` are generic over an enum tile type so consumers can supply their own tile enums; `TileType` (Room/Path/Wall/Water/Hole) with concrete `TileData` and `DefaultDungeonSetting` (a `ScriptableObject`, asset at `Runtime/Assets/DefaultDungeonSetting.asset`) are the built-in defaults.
- Coordinates are `Vector2Int`; the map array is indexed `Map[x, y]`.
- Generation relies on `UnityEngine.Random` (no seed injection currently).

## Code Conventions

Derived from the existing codebase — follow these when adding code:

- **Fields**: `[SerializeField] private` (or `protected` when subclasses need access) camelCase fields, exposed through PascalCase properties, usually expression-bodied (`public T Type => type;` or `{ get => x; set => x = value; }`). Public fields are not used on serialized types.
- **Documentation**: XML doc comments (`/// <summary>`) in Japanese on public/complex members. `Debug.Log` messages are in Japanese or short English.
- **Naming**: `Recursive`-prefixed methods for tree recursion on `Area`; editor test windows are named `*Tester` and registered under the `Debug/DungeonGenerator/` menu with Japanese labels.
- **Extensibility pattern**: data types are generic over an enum (`where T : Enum`) with a concrete default closing the generic over `TileType` (e.g. `TileData<T>`/`TileData`, `DungeonSetting<T>`/`DefaultDungeonSetting`). Follow this pattern for new tile-related data.
- **Editor-only inspector data** (e.g. preview colors on `TileSetting<T>`) is wrapped in `#if UNITY_EDITOR` even inside Runtime scripts.
- **Access levels**: types used only inside the package pipeline are `internal` (`Area`, and internal members of `FloorData`); the public API surface is `DungeonGenerator`, `FloorData`, `TileData`, `TileType`, and the setting classes.
- **Style**: Allman braces, 4-space indent, `var` for locals, file-scoped types one-per-file matching the file name. Files must be UTF-8.

### Assembly layout

- `DungeonGeneratorRuntime.asmdef` (Runtime) — no external references
- `DungeonGeneratorEditor.asmdef` (Editor) — references the runtime assembly; internal types (`Area`, `Room` internals, `FloorData` internals) are only accessible within the runtime assembly
